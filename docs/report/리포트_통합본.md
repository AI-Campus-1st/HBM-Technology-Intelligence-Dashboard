## 0. 핵심 요약

> 담당: 공동 · 2026-11-20 · 숫자는 1~7장과 대시보드 '요약' 화면(저장된 분석 결과로 계산)에서 옮겼다. 장을 고치면 여기 숫자도 함께 확인한다.

### 0.1 질문과 답

- **사용자:** 증권사 반도체 담당 애널리스트 (공개 자료 기반 기술 인텔리전스, 투자 의견 없음 — 1.3)
- **질문:** HBM에서 지금 무슨 일이 일어나고 있고, 그 판단의 근거는 무엇인가
- **답:** HBM 보도는 2024-12에 정점(월 비중 21.3%)을 찍은 뒤 2차례 다시 급증했고, 최근 3개월 평균은 2.8%로 식었다. **보도는 삼성전자 사건에 몰렸지만, HBM 실적 성장은 SK하이닉스 공시에서 확인된다.**

### 0.2 데이터와 방법

| 단계 | 내용 | 규모 | 장 |
|---|---|---|---|
| 뉴스 | 반도체 뉴스 묶음, 2023-10-19 ~ 2026-10-19 | 7,177건 → 중복 제외 6,953건 → HBM 기사(핵심·관련) 385건 | 2 |
| 공시 | DART, SK하이닉스·삼성전자, 같은 기간 | 목록 568건 → 원문 380건 → RAG 대상 101건(실적 첨부 PDF 27건 포함) | 2 |
| EDA | 월별 HBM 보도 비중, 급증 탐지(직전 6개월 평균 + 2σ, 10건 이상) | 급증 6구간 탐지 → 공시로 확인된 4구간 분석 | 3 |
| AI 이슈 분석 | LLM(`gpt-6-luna`)으로 기업별 감성(SK하이닉스·삼성전자 따로) | 385건 전수, 사람 검수 50건 + 교차 25건 | 4 |
| 공시 Q&A | 청크 → 임베딩 → 하이브리드 검색 → 근거 기반 답변·거절 | 청크 2,191개, 평가 질문 24 + 12개 | 5 |
| 대시보드 | Streamlit: 요약 → 이슈 분석 → 공시 Q&A, 저장된 결과만 조회 | 테스트 377개 | 6 |

### 0.3 핵심 발견

1. **무슨 일이 있었나 — 급증 4구간은 정책과 실적 발표가 이끌었다.**
   - 2024-10: 삼성전자 3분기 실적 콘퍼런스콜
   - 2024-12 ~ 2025-01: 미국 대중 HBM 수출 통제
   - 2025-04 ~ 05: 삼성 1분기 'HBM 쇼크'
   - 2025-12 ~ 2026-03: 두 회사의 HBM4 경쟁
   - 모두 같은 시기 공시(잠정실적·첨부 자료)로 사건이 확인된다. 공시는 급증의 원인이 아니라 근거로만 쓴다 (3.5).
2. **누구 이야기였나 — 보도는 삼성전자에 쏠렸다.**
   - 급증 구간에서 삼성전자 언급 비율은 53~95%다(구간 밖 50%).
   - 부정 보도 비율은 삼성전자 38%, SK하이닉스 21%다.
   - 삼성전자 논조(분기 순감성)는 2025Q2 −0.49(51건)가 바닥이었다. 이후 2025Q4 +0.93(27건)까지 올랐다가 최근 2026Q3 +0.17(18건)로 다시 낮아졌다 (4장, 6.5.1).
3. **공시로 확인된 사실 — SK하이닉스의 HBM 성장은 보도가 아니라 공시에서 보인다.**
   - SK하이닉스 2024년 3분기: "HBM 매출 QoQ +70% 이상, YoY +330% 이상" (첨부 p.5)
   - SK하이닉스 2025년: "HBM 매출 전년 대비 2배 이상 확대" (첨부 p.8)
   - 삼성전자 2025년 1분기: "첨단 반도체 수출 통제 영향 등에 따른 HBM 판매 감소 및 가격하락" (첨부 p.8)
   - 수집한 뉴스에서 분기 실적 공시(각 12회) 전후 실적 기사는 SK하이닉스 5건, 삼성전자 33건이다. 그래서 이 데이터의 보도량만으로 SK하이닉스의 HBM 실적을 판단하기는 어렵다. 언론 전체의 보도량을 뜻하지는 않는다 (6.5.1).

### 0.4 AI 결과의 신뢰도

| 항목 | 결과 | 읽는 법 |
|---|---|---|
| 기업별 감성 분류 (`sent_v2`) | 정확도 SK하이닉스 0.78 · 삼성전자 0.88 (Macro-F1 0.80 · 0.87) | 사람 라벨 50건 기준이다. 규칙을 만든 같은 표본이라 낙관적일 수 있다 (4.5, 7.1) |
| 공시 Q&A | 21/24 (답변 16/19, 거절 5/5, 지어낸 답변 0건) | 틀린 3개는 모두 검색 누락이다. 재정렬을 쓰면 검색 19/19, 답변은 실행마다 21~23/24 (5.4, 7.4) |
| HBM 기사 태깅 | 분석 대상 추정 정밀도 0.83, 재현율 0.85 | 태깅이 놓친 기사는 비중·감성에서 빠진다 (2.5) |

### 0.5 애널리스트에게 권하는 다음 단계

원칙: HBM 경쟁 구도는 보도량·논조가 아니라 실적 공시의 HBM 지표로 판단하고, 보도는 사건 시점을 확인하는 데만 쓴다.

1. **SK하이닉스는 보도량으로 판단하지 않는다.** 리포트의 비교 기준은 공시 수치로 잡는다.
2. **삼성전자 HBM4 반등은 정성 근거까지만 쓴다.** 실적 자료에는 'HBM4 양산 판매 개시'(2026-04-30)와 '공급 확대'(2026-07-30)가 있지만 출하량·매출 수치는 없다.
3. **관심 둔화를 사업 둔화로 읽지 않는다.** 최근 3개월 보도 비중 2.8%는 보도 관심이 줄었다는 뜻일 뿐이다.
4. **공시로 못 메우는 부분은 IR로 보완한다.** HBM 투자액은 공시로 확인할 수 없다(R&D·시설투자는 회사 전체 금액). 컨퍼런스콜·IR 질의로 보완한다.

공개 자료(뉴스·DART 공시) 기반 분석이며 투자 의견이 아니다 (6.5).

### 0.6 한계

- 보도 비중·점유·논조는 시장 점유율이나 실적이 아니다 (1.6).
- 뉴스는 지정 키워드로 수집해 실적 보도가 적게 담겼을 수 있다 (7.3).
- 급증 구간 '확정'은 탐지 결과를 본 뒤 정한 사후 기준이다 (3.5).
- 감성과 Q&A 평가는 작은 표본이고, LLM 출력은 같은 입력에서도 흔들린다 (7.1, 7.4).

## 1. 분석 목적

> 담당: 공동 · 작성: Day 1 초안, 초안 v1.2 기준으로 갱신. 실측 수치는 2~6장, 결론 요약은 0장

### 1.1 기획 배경

AI 반도체 수요가 늘면서 HBM(고대역폭 메모리)이 메모리 업계의 핵심 경쟁 축이 되었다. SK하이닉스와 삼성전자에 대한 HBM 보도는 많지만 중복·재배포가 많다. 그래서 어떤 시점에 무엇이 변했는지, 그 변화가 각 기업의 공개된 연구개발·투자 활동과 어떻게 연결되는지 판단하기 어렵다.

이 프로젝트는 **HBM 이슈 비중 변화 → 급증 시점 탐지 → 기업별(SK하이닉스·삼성전자) 보도·감성 비교 → 공시 근거 확인**이라는 분석 흐름을 구현한다.

### 1.2 대상 산업과 기업

| 항목 | 내용 |
|---|---|
| 산업군 | 반도체 |
| 대상 기업 | **SK하이닉스** (비교: **삼성전자**) — 두 기업 모두 DART 공시 수집 |
| DART 고유번호 | SK하이닉스 `00164779` · 삼성전자 `00126380` (`src/dart/corp_code.py`로 확인) |
| 분석 기술 범위 | **HBM 단독 분석 (2026-11-16 확정).** 제목 기사(핵심)가 HBM 205건인 데 비해 첨단 패키징 57건·DRAM 27건이라 월별 급증 탐지 등 독립 분석이 어렵다. 급증 탐지·LLM 분류·대시보드·결론은 HBM만 다루고, 패키징·DRAM 태그는 HBM 기사 안의 보조 정보로만 쓴다 |
| 뉴스 데이터 | 제공 반도체 묶음 7,177건 (`04_반도체_묶음`, 81개 매체) |
| 뉴스 키워드 | `반도체 R&D`(기술 및 트렌드) · `반도체 밸류체인`·`반도체 원자재`(공급망 및 인프라) · `반도체 수출 통제`·`반도체 세제 혜택`(규제 및 정책) |

### 1.5 목표와 성공 기준

**목표:** 최근 3년(2023-10-19 ~ 2026-10-19) 반도체 뉴스와 SK하이닉스·삼성전자 DART 공시를 통합 분석하여 HBM 이슈의 비중 변화와 급증 시점을 탐지하고, 기업별 보도·감성 차이와 공시 근거를 비교한다. 이를 통해 근거와 한계를 명시하는 애널리스트용 기술 인텔리전스 대시보드를 구축한다.

**성공 기준:** 사용자가 HBM 이슈의 변화, 변화가 나타난 이유, 기업별 차이, 연결 가능한 공시 근거, 추가 확인이 필요한 사항을 한 화면 흐름에서 파악할 수 있다.

**주요 판단 기준 (Day 1 확정)**
- 관심도: HBM 관련 기사 수 ÷ 같은 달 전체 기사 수
- 관련도: 핵심(제목에 HBM) / 관련(본문 5회 이상) — 기본 분석은 핵심+관련
- 급증 구간: 월별 HBM 비중이 직전 6개월 평균 + 2σ를 넘는 달, 연속된 달은 한 구간 그리고 HBM 기사 10건 이상 (최소 기사 수 조건은 Day 3 EDA 후 확정, 3.1)

### 1.6 해석 원칙

1. 기사 **절대량이 아니라 비중**으로 관심도를 판단한다. 전체 수집 기사 수가 분기마다 크게 달라서 절대량만 보면 정점을 잘못 읽는다.
2. 보도 점유율·감성 ≠ 실제 시장 점유율·사업 성과
3. 기업 전체 R&D 지출액 ≠ HBM 투자액. 사업 구조가 다른 삼성전자와 전체 수치를 직접 비교하지 않는다.
4. 같은 시점에 뉴스·공시가 있다고 두 사건의 인과관계가 성립하지 않는다.
5. 첫 달(2023-10, 13일분)과 마지막 달(2026-10, 19일분)은 일부 기간만 있으므로 월별 비중 해석 시 표시한다.

### 2.5 HBM 기사 선정 (태깅)

자세한 검수 과정은 4장에서 다루고, 여기서는 분석 대상을 정한 기준만 적는다.

- 규칙: `src/news/tagging.py` `regex_v3` — 제목 포함이면 **핵심**, 본문 5회 이상이면 **관련**, 1~4회면 **언급**
- 분석 대상: HBM 핵심+관련 385건 (Day 3 `preprocess` 중복 제외 기준, 핵심 192·관련 193). 사람 검수(관련 30건, 김한승) 기준 '관련' 정밀도 0.67 → 분석 대상 추정 정밀도 0.83, 재현율 0.85
- 기업 태그(SK하이닉스·삼성전자)는 이름만 나열된 기사가 많아 **HBM 핵심·관련 기사 안에서만** 집계한다
- 검수 라벨: HBM 관련 30건은 사람 판정, 나머지 층(핵심·언급·기업)은 1차 자동 판정. 사람과 자동 판정의 일치율 0.70(κ=0.18)로 낮아 자동 판정만으로 정밀도를 주장하지 않는다

### 3.2 공시 건수 추이 (한도윤)

> 코드: `src/eda/disclosure_trend.py` / 결과: `outputs/reports/disclosure_monthly_counts.csv`, `disclosure_type_distribution.csv`, `disclosure_category_counts.csv`, `disclosure_event_timeline.csv`, 그림 `outputs/figures/disclosure_monthly.html`

#### 집계 방법
- **기업 × 유형 × 월** 건수를 0건인 달까지 채워 센다. 뉴스 기사량과 같은 월 축으로 비교하기 위해서다.
- 유형 합계만 보면 정기성 공시에 묻힌다. 그래서 공시명으로 **공시 성격**을 붙이고, 회사의 사업 변화를 알리는 **사건성 공시**(투자·설비, 실적, 사업계획, 풍문·해명, 공급계약)를 따로 센다. 분류 규칙은 `CATEGORY_RULES`에 있다.

1. **월 공시 건수 합계는 이슈 지표로 쓰기 어렵다.** SK하이닉스 공시가 가장 많은 달은 2024-12(18건)인데, 그중 14건이 J 공정위 거래(계열사 상품·용역거래 분기 공시)다. 같은 달 사건성 공시는 1건(인디애나 HBM 패키징 공장 투자, 2024-12-20)이다. → 급증 비교에는 **사건성 공시 건수**를 쓴다.

2. **SK하이닉스 R&D는 늘었지만(2023년 대비 2025년 +61%) 매출 대비 비율은 12.8%에서 6.9%로 낮아졌다.** 매출이 R&D보다 더 빨리 늘었기 때문이다. 비율 하락을 R&D 축소로 해석하지 않는다.
3. **HBM 서술은 주로 '기타 참고사항'(업계·회사 현황)과 연구개발 섹션에 있다.** 공시 Q&A(Day 5)는 이 섹션들을 우선 청킹한다.

#### 해석 유의점
- R&D 총액과 시설투자액은 HBM 투자액이 아니다. 두 회사 모두 기술별 금액은 공시하지 않는다.
- 삼성전자 R&D는 회사 전체 값이라 SK하이닉스와 금액을 직접 비교하지 않는다. 투자 비교는 DS 부문 값을 쓰되, DS에도 파운드리·시스템LSI가 포함된다는 점을 함께 적는다.
- 분기·반기 값은 그해 누계라서, 분기별 변화를 보려면 직전 보고서 값을 빼야 한다.

### 4.2 프롬프트 설계 (`sent_v1`)

> 코드: `src/llm/prompts.py` (버전 기록은 파일 머리 주석)

- **기업별 감성:** 기사 하나를 SK하이닉스 관점·삼성전자 관점으로 **따로** 판정한다. 같은 기사가 한 기업엔 호재, 다른 기업엔 악재일 수 있어서다 (예: "삼성 HBM 인증 지연" → 삼성 부정, SK 중립 또는 긍정). 기사 전체 감성 하나로는 페르소나(반도체 애널리스트)의 비교 질문에 답할 수 없다.
- **라벨 4개:** 긍정 / 중립 / 부정 / 해당없음 (정의는 초안 v1.2 §5 C, 기준은 '해당 기업의 HBM 사업 관점'). '해당없음'을 따로 둬서 "등장하지 않음"과 "등장했지만 중립"을 구분한다.
- **판정 규칙 6개:** ① 두 기업 따로 ② 기사에 나온 사실·평가만 근거(기사 밖 지식·주가 전망 추론 금지) ③ 이름만 스치면 중립 ④ 약칭·인물(하이닉스·삼전·SK그룹 회장 발언) 처리 — 정규식 태깅이 놓치는 경우(3.1절 '최태원 SK회장')를 보완 ⑤ 호재·악재가 섞이면 중심 사건 기준, 어려우면 중립 ⑥ 이슈 키워드 1~5개(기업명 단독 금지)
- **출력:** JSON 하나 `{"sentiment_skh", "sentiment_sec", "issue_keywords"}`. API의 JSON 모드로 받고, 코드(`parse_response`)가 라벨 값·형식을 다시 검증한다. 틀리면 저장하지 않고 재시도한다.

### 4.3 실행과 재현성

- **재실행 안전:** 같은 프롬프트 버전으로 저장된 기사는 건너뛴다 → 중간에 끊겨도 다시 실행하면 남은 기사만 처리한다. 20건마다 DB에 저장한다. 버전을 올리면(`sent_v2`) 기존 결과를 지우지 않고 따로 저장해 v1·v2를 같은 표본으로 비교한다 (`news_analysis` 기본키 = 기사 + 프롬프트 버전).
- **실패 처리:** 응답 형식 오류·호출 실패는 최대 2번 재시도, 그래도 실패하면 실패 목록 CSV에 남긴다. 기사 5건이 **연속** 실패하면 남은 기사를 호출하지 않고 멈춘다 (아래 사례 이후 추가).
- **실행 중 문제와 해결 (2026-11-19):**
  1. `.env` 없음 → API 호출 전 중단 (비용 0).
  2. 20건 점검에서 20건 모두 `TypeError: Decompressor.decompress() got an unexpected keyword argument 'output_buffer_limit'`. 진단 결과 `urllib3` 2.8.0이 쓰는 인자를 오래된 `brotlicffi` 1.1.0.0이 지원하지 않는 패키지 호환 문제였다 (코드·프롬프트 문제 아님). `brotlicffi` 업그레이드로 해결. 이 과정에서 20건 × 3회 = 60회 호출이 응답 해제 단계에서 실패했다.
  3. 같은 오류로 호출만 반복하는 것을 막으려고 연속 실패 중단을 넣었다. 두 번째 실행에서는 5건 만에 멈춰 15건을 호출하지 않았다.
  4. 팀 패키지 버전을 requirements에 고정했다(#45, pandas 3.1.1 등). `brotlicffi`는 requirements에 없는 간접 의존성이라 고정 대상 추가를 논의 중이다.

- **사람끼리 일치도 (라벨 수정 후, 25건):** SK하이닉스 0.72 (κ 0.57), 삼성전자 0.68 (κ 0.57). v2와 교차 검수자의 일치율(0.88·0.84)이 사람끼리보다 높다. 감성 판정은 사람 사이에서도 갈리는 과제이므로 정확도를 '정답과의 일치'로만 읽지 않는다.
- **v2 라벨별:** '해당없음' F1이 두 기업 모두 1.00 (v1 SK 0.71). SK '부정' 재현율 0.33 → 0.67. 반면 SK '긍정' 정밀도 0.57 (예측 21건 중 정답 13) — v2가 긍정을 많이 낸다 (4.6절 ⑥).
- **채택:** 대시보드·SQL 04는 `sent_v2`를 쓴다. SK하이닉스는 모든 지표가 올랐고 삼성전자는 같다.
- **주의 — 낙관적 추정:** v2 규칙은 이 50건의 오류를 보고 만들었으므로, 같은 50건으로 잰 v2 점수는 실제보다 높게 나올 수 있다. 라벨하지 않은 51~100행 일부를 v2 확정 후 라벨하면 독립 검증이 된다 (후속 과제).

> v1 불일치(라벨 수정 전) SK 18건·삼성 8건을 하나씩 분류하고, v2에서 어떻게 바뀌었는지 확인했다. ①·②의 v2 결과는 라벨 수정 후 기준.

### 5.1 청킹 (한도윤, Day 3)

> 코드: `src/rag/chunking.py` (`python -m src.rag.chunking`) / 결과: `data/processed/disclosure_chunks.jsonl`(git에 올리지 않음), 요약 `outputs/reports/disclosure_chunk_summary.csv`

#### 대상과 단위
- **대상:** DB `disclosure`에서 원문을 확보했고 `rag_target=1`인 공시 **101건** (첨부 반영 전 75건). RAG 대상은 `news_link --apply`(`link_v2`)가 정한다: A 정기보고서 + 본문 HBM 언급 + 실적 외 주제로 HBM 기사와 연결된 공시 (리포트 2.3·초안 §11 논의 질문 7) + **첨부 경영설명회 자료에 HBM이 나오는 실적 공시 26건** (2026-11-18 추가, 아래 '첨부 경영설명회 자료'). 청킹은 DB에 적힌 값을 그대로 따르므로, 기준이 바뀌면 `news_link --apply` 다음에 다시 실행만 하면 된다.
- **정기보고서(A):** 본문 전체(건당 20만~70만 자, 대부분 재무제표)를 쓰지 않는다. 3.3절의 사업·제품·투자·연구개발 섹션만 쓴다. 삼성전자 연구개발실적(상세)은 TV·모바일 같은 DX 부문이 대부분이어서 **DS 부문 부분만** 남긴다.
- **그 밖의 공시(B·D·I·J):** 본문 전체를 섹션 '본문' 하나로 본다. 섹션 성격에는 공시명으로 정한 공시 성격(투자·설비, 풍문·해명 등, 3.2절)을 넣는다.

#### 첨부 경영설명회 자료 (2026-11-18 추가, 초안 §11 논의 질문 8)

> 코드: `src/dart/collect_attachments.py` / 결과: `data/raw/dart/attachments/`(PDF·목록 `attachment_list.csv`), `data/processed/disclosure_attachments.jsonl`

- **왜 넣나:** 영업(잠정)실적 공시의 본문은 숫자 표뿐이다. HBM 판매와 전망에 대한 회사 발언은 첨부한 경영설명회 PDF에 있다. 예: SK하이닉스 '24.3Q 자료의 "HBM 매출 QoQ +70% 이상". 이 첨부가 없으면 "분기별 HBM 실적은?" 같은 질문에 근거를 댈 수 없다. 근거 공시 판정(3.5절)도 이 첨부를 보고 했다.
- **어떻게 받나:** 첨부는 OpenAPI 원문 zip에 없다. 그래서 DART 웹 화면의 '첨부' 목록에서 다운로드 화면으로 들어가 개별 파일을 받는다. 요청 사이에 1초씩 쉰다.
  - 대상: 공시명에 '영업(잠정)실적'이 있는 공시 36건
  - 받는 파일: PDF이고 국문인 것 (SK하이닉스 `_KOR.pdf` 12건, 삼성전자 15건). 영문 12건은 내용이 같아 뺀다. [기재정정] 9건은 첨부가 없다.
  - 삼성전자 [기재정정] 3건의 첨부는 월초 잠정실적 설명 자료(1쪽)다. 이 첨부는 정정 전 원래 공시 번호(예: `20241008800067`)에 붙어 있다. DB에는 정정 공시 번호만 있어서 첨부를 원래 번호로 받고, 청크는 DB에 있는 정정 공시에 붙인다.
- **추출:** `pypdf`로 쪽마다 텍스트를 뽑는다. 27개 파일, 413쪽, 약 16만 자이고 HBM이 132번 나온다. 30자 미만인 쪽(표지·간지)은 청크로 만들지 않는다.
- **RAG 대상:** 첨부에 HBM이 나오는 공시 26건을 RAG 대상에 넣었다. 본문 HBM 기준(2)을 첨부에도 똑같이 적용한 것이다. 빠진 1건은 HBM 언급이 없는 삼성전자 '24.4분기 잠정실적 설명 자료다.
- **실적 연결 제외 규칙과의 관계:** `link_v2`의 '실적 주제로만 연결된 공시는 RAG에서 제외' 규칙은 그대로 둔다. 실적 공시는 기사와 연결돼서가 아니라 첨부 내용 때문에 RAG에 들어간다.

#### 자르는 방법
- **표 행 묶기:** DART 표는 텍스트로 바뀌면 칸마다 줄이 나뉜다. 30자 이하 줄이 이어지면 ` | `로 묶는다. 예: `연구개발비용 합계 | 6,732,527 | 4,954,447 | …`. 항목 이름과 값이 다른 청크로 갈라지지 않게 하기 위해서다. '가.', '(1)', '2. ' 같은 소제목은 묶지 않는다.
- **크기:** 1,000자, 앞뒤 청크 겹침 150자. LangChain `RecursiveCharacterTextSplitter`로 줄 → 표 칸(` | `) → 문장 → 공백 순서로 자를 곳을 찾는다. 30자 미만 조각은 버린다.
- **머리말:** 청크 앞에 `[기업 | 공시명 | 제출일 | 섹션]`을 붙인다. 본문에 회사명이나 시점이 없어도 "삼성전자 2025년 시설투자" 같은 질문에 검색되게 하려는 것이다.
- **첨부:** 섹션 '첨부'(성격 'IR자료')로 쪽마다 따로 자른다. 슬라이드 한 쪽은 대부분 1,000자보다 짧아 쪽 하나가 청크 하나가 된다. 머리말은 `[기업 | 공시명 | 제출일 | 첨부 <파일명> p.N]`이다.
- **메타데이터:** `chunk_id`(`<rcept_no>_<섹션 순번>_<청크 순번>`, 첨부는 `<rcept_no>_a<첨부 순번>p<쪽>_<청크 순번>`, 다시 실행해도 같다), `rcept_no`, `corp_code`, `corp_name`, `report_nm`, `rcept_dt`, `pblntf_ty`, `url`, `section`, `section_type`, `file_name`, `page`, `chunk_index`, `n_chars`, `has_hbm`. 답변에 근거로 표시할 공시명·제출일·링크·첨부 쪽 번호와 기업 필터에 필요한 값이 모두 들어 있다. 본문 청크는 `page=0`, `file_name=''`이다. Chroma 메타데이터에는 None을 넣을 수 없기 때문이다.

- **다음 단계(`qa_chain`)에 반영할 것:** 질문에 기업이 나오면 `corp_name` 메타데이터 필터를 건다. 임베딩만으로는 'SK하이닉스'와 '삼성전자' 자료가 섞인다. 위임장(D) 쏠림은 아직 나타나지 않았지만 평가 질문을 늘려 다시 확인한다.

### 5.3 질의응답 체인 (한도윤, Day 5)

> 코드: `src/rag/qa_chain.py` (`python -m src.rag.qa_chain "질문"`, 예시 묶음 `--samples`) / 결과: `outputs/reports/qa_samples.csv`

#### 흐름
1. **기업 필터:** 질문에 한 기업만 나오면 그 기업 청크만 검색한다(`corp_name` 메타데이터). 두 기업이 다 나오는 비교 질문은 기업마다 3개씩 따로 검색해 번갈아 합친다. 한 번에 검색하면 SK 청크만 6개가 나와 "비교할 수 없다"고 답했다.
2. **하이브리드 검색:** 벡터 검색으로 후보 40개를 뽑고, 그 안에서 키워드 점수(BM25)로 한 번 더 순위를 매긴다. 두 순위를 RRF(Reciprocal Rank Fusion)로 합쳐 상위 6개를 쓴다. 한글은 2글자 단위로 잘라 조사가 붙어도 맞게 했다('판매가' → 판매·매가).
   - 이유: 벡터만 쓰면 표현이 다른 슬라이드 문장이 밀린다. "삼성전자가 HBM 판매가 줄었다고 밝힌 이유는?"의 근거('25.1Q 경영설명회 p.8 "첨단 반도체 수출 통제 영향 등에 따른 HBM 판매 감소")가 벡터 15위였는데, 하이브리드 재정렬 후 3위가 됐다.
3. **1차 거절 (검색 거리):** cosine 거리 0.65보다 먼 청크는 버린다. 남는 청크가 없으면 LLM을 부르지 않고 거절한다. 표본 확인 결과 공시와 관련된 질문의 최근접 거리는 0.38~0.54였고, 공시와 무관한 질문(날씨·요리)은 0.76 이상이었다.
4. **답변:** LLM은 `gpt-6-luna`(`config.LLM_MODEL`, 프로젝트 공통 모델)를 쓴다. 근거를 [1]~[6] 번호로 주고 구조화 출력(`answerable`, `answer`, `used_sources`)으로 받는다. 프롬프트 규칙은 다음과 같다: 근거 안의 내용만 쓴다, 문장마다 번호를 단다, 수치는 단위까지 그대로 쓴다, 다른 기업·시점의 자료로 대신 답하지 않는다, 전망은 "회사는 ~라고 밝혔다"처럼 쓴다.
5. **2차 거절 (LLM 판단):** LLM이 근거로 답할 수 없다고 하면 정해진 거절 문구를 돌려준다. 답할 수 있으면 LLM이 실제로 쓴 번호의 출처만 붙인다. 출처에는 기업, 공시명, 제출일, 위치(섹션 또는 '첨부 파일명 p.N'), 거리, DART 링크가 들어간다.

### 5.4 검색·답변 평가 (한도윤, Day 5)

> 코드: `src/rag/evaluate.py` (`python -m src.rag.evaluate`) / 평가 질문: `data/labels/qa_eval_v1.csv` / 결과: `outputs/reports/qa_eval_v1.csv`, `qa_eval_v1_summary.csv`

#### 평가 방법
- **질문 24개:** 답변 질문 19개와 거절 질문 5개다. 5.3의 예시 질문과 달리, 질문마다 사람이 청크 원문을 찾아 **정답 근거 공시**와 **핵심 사실**(정규식)을 미리 정했다.
  - 답변 질문 유형: 첨부 IR 자료(수치·시기·이유·계획), 공시 본문 수치, 정기보고서(R&D·시설투자), 풍문 해명·조회공시 답변, 위임장(D), 두 회사 비교, 기업 이름이 없는 질문

  - 답변 정확: 답했고, 핵심 사실이 있고, 붙인 출처에 정답 근거가 있어야 한다.
  - 거절 정확, 위임장(D) 비중, 최근접 거리

- **'과소 보도' 표현 검토:** "실적 보도가 거의 없어 … 과소평가"는 근거 숫자가 없는 단정이다. 수집한 뉴스에서 각 회사 분기 실적 공시(영업(잠정)실적, 2024–2026 각 12회) 전후 D-1–D+3에 제목에 실적·매출·영업이익(영업익)이 들어간 HBM 기사(중복 제외, HBM·기업 태그 핵심·관련)는 SK하이닉스 5건, 삼성전자 33건이었다(DB 직접 집계, 2026-11-20). 인용한 SK 두 실적 발표(2024-10-24, 2026-01-28) 전후 창에는 SK 실적 기사가 0건이고, 2024-10-23–27에는 SK하이닉스 태그(핵심·관련) 기사 자체가 없다. 다만 뉴스는 반도체 R&D·밸류체인·수출 통제·세제·원자재 키워드로 수집해 실적 기사가 적게 담겼을 수 있으므로, 결론은 '수집한 뉴스 데이터 안의 결과'로 한정하고 언론 전체가 덜 보도했다는 주장은 하지 않는 것을 제안한다. 제안 문장: "수집한 뉴스에서 각 회사 분기 실적 공시 전후 실적 기사는 SK하이닉스 5건, 삼성전자 33건이다. 이 데이터의 보도량·점유만으로 SK하이닉스의 HBM 실적을 판단하기는 어렵다(언론 전체 보도량을 뜻하지는 않는다)." → **반영 (2026-11-20, 한도윤 합의):** 요약 카드 ③과 권고 ①의 문장을 제안 문장으로 바꿨다. 숫자는 `earnings_news_counts`를 다시 살려 화면을 열 때 계산한다(SK하이닉스 5건·삼성전자 33건, 각 12회). 테스트가 '과소평가'·'거의 없다' 같은 단정 표현이 없는지 검사한다.

### 7.3 데이터·방법의 한계 (김한승)

- **뉴스 수집 범위:** 반도체 R&D·밸류체인·수출 통제·세제·원자재 등 지정 키워드로 수집해 실적 보도가 일부 누락됐을 수 있다. 기업별 영업(잠정)실적 공시일 전후(D-1~D+3)에, 제목에 실적·매출·영업이익·영업익 중 하나가 들어간 기사를 집계했다. 중복을 제외하고 HBM 태그와 해당 기업 태그가 각각 ‘핵심’ 또는 ‘관련’인 기사만 포함했다. 각 12회 공시를 기준으로 SK하이닉스 5건, 삼성전자 33건이었다. 이 수치는 수집 표본의 보도량을 보여주며, 실제 HBM 사업 성과는 공시 자료로 보완했다(6.5.1).
- **급증 탐지 방법:** 방식 A에서는 기존 급증 월이 기준선의 평균과 표준편차를 높여 뒤따르는 급증을 놓치는 경우가 있었다. 방식 B는 직전 6개월 고정 창에서 기존 급증 월을 제외하며, 빠진 월을 더 이전 월로 채우지 않는다. 최소 기준선 월수와 최소 기사 수를 바꿔 결과를 비교했으며, 일부 월의 급증 판정은 설정에 따라 달라졌다(3.1).
- **태깅 재현율:** 정규식 HBM 태깅의 추정 재현율은 0.85다. 태깅이 놓친 기사는 HBM 보도 비중의 분자에서 빠지고 감성 분석 대상에서도 제외된다(2장).
- **뉴스 지표의 해석:** 보도 비중과 기업 언급 비율은 수집 기사에서 기술과 기업이 얼마나 자주 다뤄졌는지 보여준다. 감성은 기사에서 나타난 기업별 유리·불리한 평가를 분류한 결과다. 시장점유율과 매출은 별도의 사업 자료로 확인해야 한다.

| 청크 경계 | Q19(삼성전자 2025년 사내이사 후보)는 재정렬로 정답 청크가 4위까지 올라왔지만 LLM이 거절했다. 후보 이름이 있는 청크에 '사내이사 선임' 의안 제목이 없었다 | 청크마다 `[기업 \| 공시명 \| 제출일 \| 섹션]` 머리말을 붙였다. 키워드 점수에 머리말을 넣는 시험은 다른 질문(Q02)을 틀리게 해 적용하지 않았다 | 표·의안처럼 제목과 내용이 떨어진 문서는 여전히 놓칠 수 있다 |
| 같은 근거, 다른 출처 선택 | 재정렬 평가를 두 번 돌리자 검색 결과(근거 6개와 순서)가 같은데도 답변 정확이 23/24·21/24로 달랐다. 같은 근거로 4번 반복하면 Q16은 1/4, Q18은 4/4 맞았다 | 점수를 한 번의 숫자가 아니라 범위(21~23/24)로 적었다. `temperature=0`(추론을 꺼야만 받음)은 Q16 2/4, `seed=42`는 효과가 없어 적용하지 않았다 | 저장된 예시 답변도 다시 만들 때마다 문장·출처 수가 조금씩 달라진다(비교 질문 출처 4 → 3건) |
| 평가 정답의 사후 보정 | 결과를 본 뒤 정답 근거를 두 번 추가했다. Q12(1차 20/24 → 21/24)와 Q10(재정렬 후)은 출처로 단 공시에도 같은 사실이 원문에 있었다 | 보정마다 원문을 확인하고, 보정 전 점수와 이유를 리포트에 그대로 적었다(5.4). 같은 경우인 Q18은 보정이 반복되지 않도록 고치지 않았다. 재정렬을 시험하기 전에 새 평가 질문 12개(`qa_eval_v2`)를 먼저 만들어 두 세트로 확인했다 | 평가 질문 24+12개를 한 사람이 만들고 정답도 정했다. 88%는 대략적인 수준으로만 본다 |
| 실시간 호출과 '저장된 결과만' 원칙 | 자유 질문은 미리 답을 만들어 둘 수 없어, 대시보드가 저장된 결과만 읽는다는 원칙과 부딪혔다 | 예시 질문 9개는 저장된 답변(`qa_samples.json`, 커밋)으로 보여 주고, 직접 입력한 질문만 실시간으로 호출한다(5.5). 키·벡터 DB가 없거나 발표 중 네트워크가 끊겨도 예시 답변은 보인다 | 직접 질문의 답은 검증되지 않은 실시간 결과다. 화면 아래에 원문 확인을 권하는 문구를 두었다 |

정리하면, 지어낸 답변은 거절 단계에서 막혔고, 오답은 대부분 정답 근거를 찾지 못한 검색에서 나왔다. 그래서 개선은 LLM 프롬프트가 아니라 검색(하이브리드·기업별 검색·재정렬)과 검색 대상(첨부 PDF)에 집중했다. 남은 문제는 같은 근거로도 LLM이 출처를 다르게 고르는 흔들림과, 결과를 본 뒤 정답을 고치는 일이 평가를 낙관적으로 만들 수 있다는 점이다. 다음 평가에서는 정답 근거 기준(같은 사실이 있는 다른 공시를 인정할지)을 평가 전에 정하고, 같은 질문을 여러 번 돌려 점수를 범위로 보고한다.

#### 협업 방식

- **브랜치·PR:** `main`에 직접 커밋하지 않고 브랜치와 PR로만 합쳤다. 리포트를 장별 파일로 나눠 동시에 써도 충돌이 적었다. 그래도 같은 파일(리포트 6장, README, `conclusion.py`)을 함께 고치면서 충돌을 여러 번 해결했다.
- **환경 차이:** pandas 2.3.3에서 공시 근거를 다시 생성하자 기존 확인 표시 7건이 해제됐다. 팀 버전인 3.1.1로 맞춘 뒤 문제가 해결됐다. 의존성 명세에는 `pandas==3.1.1`과 응답 압축 해제에 필요한 `brotlicffi>=1.2`를 명시했다(#45, #51).
- **squash 머지로 사라진 변경:** 아래 PR이 머지된 뒤 위에 쌓은 브랜치를 그대로 올리자 변경이 빠지거나 두 번 들어갔다. #7은 main이 아닌 다른 브랜치로 머지됐고(#9로 다시 올림), #20 머지 때 README 행과 테스트 4개가, #25 머지 때 README 실행 순서 설명이 사라졌다(#23·#26에서 복원). 그 뒤로는 PR base를 항상 main으로 두고, 이미 머지된 브랜치에는 push하지 않으며, 머지 전 diff에서 README와 테스트 수가 줄지 않았는지 확인했다.
- **DB는 주고받지 않고 각자 다시 만들기:** SQLite 파일을 주고받으면 서로 덮어써 최신본을 알 수 없다. 대신 코드와 입력(DART 원본 zip, LLM 결과 CSV, 사람 라벨 CSV)을 공유하고 각자 DB를 다시 만든 뒤, `db --check`의 테이블별 행 수·기본키 지문·FK 위반으로 두 컴퓨터의 결과가 같은지 맞췄다(Day 2부터). 지문은 기본키만 보므로 `verified` 같은 값의 차이는 실행 출력의 건수로 따로 확인했다.
- **라벨 파일과 Excel:** 근거 확인 라벨을 Excel로 저장하자 접수번호(`rcept_no`)가 `2.0241E+13`처럼 지수 표기로 바뀌고 파일이 cp949로 저장되어 키가 깨졌다(두 번). 맨 끝에 문자열 `key` 열을 두어 키를 복구하고, 키가 깨졌는데 `key`가 없으면 실행을 멈추게 했다.
- **역할 경계:** 결론을 이슈 분석 화면과 요약 페이지 두 곳에서 만들 뻔했다. 결론은 요약 페이지(한도윤 화면, 김한승 숫자 계산·QA)로 모으고, 이슈 분석은 분석 결과만 보여 주도록 정리했다. 쓰지 않는 코드는 공동 PR로 정리했다 (#62).
- **AI 도구 사용:** 코드 작성과 점검에 Claude를 썼다. 실행 결과는 로그 파일로 공유하고, 사람이 원문(기사·공시 PDF)과 숫자를 직접 확인한 뒤 반영했다. API 키는 저장소·로그에 남기지 않았다.

### 7.6 다음에 다르게 할 것

1. 프롬프트 개선용 표본과 독립 평가용 표본을 처음부터 나눈다. 이번 프로젝트의 후속 평가에서는 프롬프트와 판정 기준을 확정한 뒤, 아직 라벨링하지 않은 51~100행을 활용한다.
2. 공시 인용은 원본 문서, 쪽 번호, 기간, 지표 정의와 함께 저장한다. 보고서와 대시보드에 표시할 인용문을 쪽별 추출 텍스트와 대조한다.
3. HBM 기술 경쟁, 실적, 고객사 공급, 투자 등 분석 질문에 필요한 주제를 반영해 뉴스 수집 키워드를 설계하고, 주제별 누락 가능성을 점검한다.
4. 프로젝트 시작 때 Python과 주요 패키지 버전을 고정하고 공통 실행·테스트 절차를 문서화한다.
5. 기업별 감성 판정 기준과 경계 사례를 검수 전에 합의한다. 판정이 갈릴 때는 기사 원문을 대조해 기준을 보완한다.
6. 평가 질문과 정답 근거 기준(같은 사실이 담긴 다른 공시도 정답으로 볼지)을 시험 전에 정한다. 이번에는 결과를 본 뒤 정답을 두 번 보정했다(7.4). 재정렬 시험 때처럼 새 기법을 시험하기 전에 확인용 질문 세트를 먼저 만들어 둔다.
7. LLM 결과는 같은 입력에서도 흔들리므로, 평가는 여러 번 실행해 점수를 범위로 보고한다.
