### 데이터 교체 경위 (회고 참고)

처음 받은 파일은 AI반도체 묶음(120,057건, 2021-10 ~ 2026-10, 키워드 `AI 반도체`)이었고 이 데이터로 기획 초안 v1.1을 썼다. 2026-11-13에 제공 데이터가 반도체 묶음(7,177건)으로 바뀌었다. 영향은 다음과 같다.

- 규모가 약 1/17로 줄어 HBM 제목 기사가 분기당 1~46건 → 급증 탐지를 주 단위에서 **월 단위**로 바꿨다.
- 가이드의 이슈 카테고리 구조를 가진 데이터가 되어 '카테고리' 필터를 그대로 쓸 수 있게 됐다.
- HBM 제목 기사 205건 중 90건이 `반도체 수출 통제` 키워드로 수집되었다. HBM 이슈가 규제 사건 위주로 보일 수 있어 카테고리별로 나눠 해석한다.
- 분석 기간을 2023-01-01 ~ 2026-09-30에서 2023-10-19 ~ 2026-10-19로 바꿨다 (`config.py`).

### 적재 과정

`python -m src.news.load_news` (`src/news/load_news.py`)

1. `config.NEWS_CSV`만 읽는다 (폴더에 다른 CSV가 있어도 무시).
2. 컬럼 변환: 제목·본문·URL·발행일·매체명·수집키워드 → `news` 테이블 컬럼.

4. `db.write_table(mode="replace")`로 저장해 다시 실행해도 결과가 같다.

### 공시 범위 (2026-11-16 확정)

#### 결정

공시 유형마다 **거르는 단계**를 다르게 둔다. 공시명만으로 내용을 알 수 있는 유형은 공시명으로, 공시명이 같아도 내용이 다른 유형은 본문으로 거른다.

| 유형 (`pblntf_ty`) | 목록 수집 | 원문 확보 | 거르는 방법 |
|---|---|---|---|
| A 정기공시 | 전체 | 전체 | 없음 |
| B 주요사항보고 | 전체 | 전체 | 없음 |
| I 거래소공시 | 전체 | 일부 | **공시명**: 신규시설투자, 단일판매ㆍ공급계약, 영업(잠정)실적, 장래사업ㆍ경영계획, 풍문·조회공시 답변, 타법인주식·유형자산 취득, 투자판단관련주요경영사항, 영업양수·양도, 기타경영사항 |

| D 지분공시 | 의결권대리행사권유참고서류만 | 그 문서만 | **공시명** |

- 걸러진 공시도 어떤 단계에서 왜 빠졌는지 기록하고 유형별 원문 확보율을 남긴다.
- EDA의 공시 건수 추이는 유형별로 나눠 보여 준다 (J는 분기마다 반복 공시라 합치면 다른 유형의 변화가 묻힌다).

### 수집 과정

#### 1단계 — 목록 수집 (`python -m src.dart.collect_list`, 2026-11-16)

- `list.json`을 기업 2개 × 유형 5개(A·B·D·I·J)로 요청했다. `last_reprt_at=Y`로 정정공시는 최종본만 받고, 페이지당 100건, 요청 사이 0.5초 딜레이를 두었다.
- 응답 원본은 `data/raw/dart/list/20231019_20261019/<corp_code>/<유형>_p<페이지>.json`에 저장한다. 다시 실행하면 저장된 응답을 쓰므로 API를 부르지 않는다 (첫 실행 54회 호출, 재실행 0회).
- 오류 응답(키 오류·한도 초과 등)은 저장하지 않고 멈춘다. 데이터 없음(013)은 빈 결과로 처리한다.

- 목록을 다시 수집해도 이미 처리한 원문 결과(`text`·`text_status`·`rag_target`·`filter_reason`)는 유지한다.

#### 2단계 — 원문 다운로드 (`python -m src.dart.collect_documents`, 2026-11-16)

- 원문 대상 380건: A·B·D·J 전부, I는 공시명 필터(시설투자·공급계약·잠정실적·장래사업계획·풍문 해명·주식/자산 취득·영업양수도·기타경영사항, 단 '배당'이 들어간 공시명 제외)에 걸린 101건.
- I 나머지 188건은 `text_status='대상아님'`, `filter_reason='I_공시명'` (배당, IR 개최 안내, 최대주주 지분 변동, 주총 소집 등).
- 공시서류원본파일 API(`document.xml`)로 zip을 받아 `data/raw/dart/documents/<rcept_no>.zip`에 저장. 요청 사이 0.5초, 이미 받은 zip은 건너뛴다 (377회 호출, 실패 0건).
- 실패하면 `실패`·`다운로드오류: …`로 기록하고 다시 실행하면 재시도한다. 키 오류·한도 초과는 바로 멈춘다.

#### 3단계 — 텍스트 추출 (`python -m src.dart.parse_documents`)

- zip 안의 본 문서(`<rcept_no>.xml`)만 읽는다. 감사보고서 등 첨부 문서는 쓰지 않는다.
- 원문 형식은 DART XML과 HTML 두 가지. 태그를 지우고 문단·표 행은 줄바꿈, 표 셀은 ` | `로 나눈다. 인코딩은 UTF-8, 안 되면 CP949.
- 50자 미만이면 본문을 못 뽑은 것으로 보고 `실패`·`본문없음`으로 기록한다 (해당 0건).
- 본문 길이: 중앙값 1,140자, 합계 약 1,302만 자. 정기보고서는 건당 19.7만 ~ 71.5만 자.

#### D 위임장 참고서류 — 중복 아님

같은 해에 2건씩 있는 경우(예: 삼성전자 2026-03-12 두 건)를 확인했다. 긴 문서(3만 ~ 8만 자)는 회사가 낸 주총 참고서류이고, 짧은 문서(3,600 ~ 8,000자)는 전자위임장 플랫폼 등 다른 권유자가 낸 별개 공시라 둘 다 둔다. HBM은 회사 문서 5건에만 나온다.

## 2.4 통합 스키마

SQLite(`data/db/hbm.db`), 정의는 `src/common/schema.py`·`docs/schema.md` v1.2. 두 사람이 각자 같은 코드와 입력으로 DB를 만들고 `--check`로 맞춰 본다 (`docs/conventions.md` §5).

| 테이블 | 담당 | 내용 |
| --- | --- | --- |
| `news` | 김한승 | 뉴스 원본 + 카테고리 + 중복 표시 |
| `news_tag` | 김한승 | 정규표현식 기술·기업 태그와 관련도 등급 (기사당 여러 행) |
| `news_analysis` | 김한승 | LLM 기업별 감성·이슈 키워드 (프롬프트 버전별) |
| `issues` | 김한승 | 월 단위 HBM 급증 구간 |
| `disclosure` | 한도윤 | 공시 목록·본문 |
| `issue_evidence` | 공동 | 급증 구간과 기사·공시의 연결 (자동 연결은 후보) |

**설계 판단:** 규칙 태그(`news_tag`)와 LLM 결과(`news_analysis`)를 분리했다. 태그는 전체 기사에 비용 없이 붙이고, LLM은 HBM 기사에만 비용을 들여 돌리므로 범위와 버전 관리가 다르다.

## 2.5 HBM 기사 선정 (태깅)

자세한 검수 과정은 4장에서 다루고, 여기서는 분석 대상을 정한 기준만 적는다.

- 규칙: `src/news/tagging.py` `regex_v3` — 제목 포함이면 **핵심**, 본문 5회 이상이면 **관련**, 1~4회면 **언급**
- 분석 대상: HBM 핵심+관련 385건 (Day 3 `preprocess` 중복 제외 기준, 핵심 192·관련 193). 사람 검수(관련 30건, 김한승) 기준 '관련' 정밀도 0.67 → 분석 대상 추정 정밀도 0.83, 재현율 0.85
- 기업 태그(SK하이닉스·삼성전자)는 이름만 나열된 기사가 많아 **HBM 핵심·관련 기사 안에서만** 집계한다
- 검수 라벨: HBM 관련 30건은 사람 판정, 나머지 층(핵심·언급·기업)은 1차 자동 판정. 사람과 자동 판정의 일치율 0.70(κ=0.18)로 낮아 자동 판정만으로 정밀도를 주장하지 않는다
