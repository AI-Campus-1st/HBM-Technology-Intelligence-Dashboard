## 7.1 LLM 활용 한계와 대응 — 뉴스 감성 분류 (김한승)

> 근거: 4.3 실행 기록, 4.5 표본 검수, 4.6 오류 유형. 모델 `gpt-6-luna`, 프롬프트 `sent_v1` → `sent_v2`.

| 한계 | 실제로 생긴 일 | 대응 | 남은 위험 |
|---|---|---|---|
| 입력 길이 제한 | v1은 본문 1,500자만 넣어, 기업이 기사 뒤쪽에만 나오면 '해당없음'으로 판정 (오류 SK 5·삼성 4건) | v2에서 본문을 6,000자로 확대했다. 9건 모두 '해당없음'에서 다른 라벨로 바뀌었고, 이 중 수정된 사람 라벨과 일치한 것은 6건(SK 3·삼성 3)이다. | 감성 분류 대상 385건 중 7건(1.8%)은 본문이 6,000자를 초과한다. |
| 업계 공통 사건 해석 | 미국 수출 규제처럼 'K반도체' 전체 악재를 v1이 개별 기업에는 '중립'으로 판정 | 규칙 7(업계 공통 영향도 해당 기업 영향으로 본다) 추가 → 3건 중 2건 해결 | 규칙 과적용: '영향 제한적' 기사를 긍정·부정으로 판정 (새 오류 ⑥). v3 후보 규칙 |
| 같은 표본으로 튜닝 | v2 규칙을 검수 50건의 오류를 보고 만들고, 같은 50건으로 채점 | 성능이 낙관적으로 추정될 수 있음을 리포트와 이슈 분석 화면의 감성 차트 아래에 표시 | 독립 검증 없음. 라벨하지 않은 51–100행으로 확인하는 것이 후속 과제 |
| '정답' 자체의 불확실성 | 교차 검수 25건에서 사람 간 일치율은 SK 0.72·삼성 0.68(두 기업 모두 κ 0.57)이었다. 사람 라벨을 1회 수정(10칸) | 수정 전·후 점수를 모두 기록, 정확도와 함께 Macro-F1·κ·혼동행렬 보고 | 긍정/중립 경계(④)는 사람 기준이 갈려 남음 |
| 형식 오류·호출 실패 | 패키지 호환 문제로 약 75회 호출(첫 실행 20건 × 3회 = 60회, 연속 실패 중단을 넣은 두 번째 실행 5건 × 3회 = 15회, 4.3)이 응답 압축 해제 단계에서 실패 | `brotlicffi`를 업그레이드해 장애를 해결했다. 분류 코드에는 JSON 형식·라벨 검증, 최대 2회 재시도, 기사 5건 연속 실패 시 중단, 재실행 시 저장된 기사 건너뛰기를 적용했다. | 실패 호출도 과금됐을 수 있음 |
| 비용 확인 불가 | 부트캠프 발급 키라 사용량·비용을 조회할 수 없음 | 호출량·입력 글자 수·소요 시간을 기록 (4.1) | 실제 비용은 미확인 |
| 이슈 키워드 표현 분산 | '대중 HBM 수출 통제'·'반도체 수출 통제'처럼 같은 이슈가 여러 표현 | 빈도는 참고로만 사용 | 표현 정규화가 필요 |

사람이 검수한 50건에서 v1(라벨 수정 후) 대비 v2 정확도는 SK하이닉스 0.70→0.78, 삼성전자 0.88→0.88이었다. 교차 검수 25건에서 v2와 교차 검수자의 일치율은 각각 0.88과 0.84였다. 검수자 간 판정 차이와 표본 재사용을 고려하면, 새 표본을 평가하기 전까지는 이 수치를 개발에 사용한 표본의 결과로 해석해야 한다. 다음 평가에서는 전체 정확도와 함께 이전 버전에서 맞혔다가 새 버전에서 틀린 사례를 확인한다.

## 7.2 근거 문구 검증 — '사람이 확인했다'와 '원문과 같다'는 다르다 (김한승)

> 근거: 리포트 6.5.1 결론 최종 QA.

- **무슨 일이 있었나:** 결론 인용의 근거 공시 3건은 모두 `verified=1`(사람이 공시를 확인함)이었다. 확인 메모를 옮기는 과정에서 일부 인용의 비교 기준과 조건이 빠졌다.
  - SK하이닉스 '25년 자료: '전년 대비'가 빠졌고, p.8과 p.13의 두 문장이 한 문장처럼 합쳐졌다.
  - 삼성전자 '25.1분기 자료: '가격하락'이 빠졌다.
  - PDF 추출 텍스트는 단 순서가 섞여, '1분기 현황' 문구가 '하반기 전망' 아래에 있는 것처럼 보였다. PDF를 직접 열어 확인했다.

- **출처 혼동 점검:** 2024년 3분기 HBM 매출이 전 분기 대비 70% 이상 증가했다는 수치는 SK하이닉스 실적 발표 첨부 자료와 삼성전자 콘퍼런스콜에서 각각 확인했다. 결론의 인용은 SK하이닉스 첨부 자료에 해당하며, 인용에 기업명·자료명·공시일을 붙였다.
- **대응:** 인용을 PDF 원문에 맞추고 쪽 번호를 붙였다. 전처리 파일이 있을 때 쪽별 추출 텍스트에 인용문이 포함되는지 검사하는 테스트를 추가했다. 다단 편집에서 문구가 속한 항목은 PDF 화면을 직접 열어 확인했다.
- **배운 점:** 근거를 요약하거나 옮길 때 비교 기준과 조건이 빠질 수 있다. 인용문과 함께 원본 문서, 쪽 번호, 기업과 기간을 기록하면 결론 문장을 수정할 때 근거를 다시 확인할 수 있다.

## 7.3 데이터·방법의 한계 (김한승)

- **뉴스 수집 범위:** 반도체 R&D·밸류체인·수출 통제·세제·원자재 등 지정 키워드로 수집해 실적 보도가 일부 누락됐을 수 있다. 기업별 영업(잠정)실적 공시일 전후(D-1~D+3)에, 제목에 실적·매출·영업이익·영업익 중 하나가 들어간 기사를 집계했다. 중복을 제외하고 HBM 태그와 해당 기업 태그가 각각 ‘핵심’ 또는 ‘관련’인 기사만 포함했다. 각 12회 공시를 기준으로 SK하이닉스 5건, 삼성전자 33건이었다. 이 수치는 수집 표본의 보도량을 보여주며, 실제 HBM 사업 성과는 공시 자료로 보완했다(6.5.1).
- **급증 탐지 방법:** 방식 A에서는 기존 급증 월이 기준선의 평균과 표준편차를 높여 뒤따르는 급증을 놓치는 경우가 있었다. 방식 B는 직전 6개월 고정 창에서 기존 급증 월을 제외하며, 빠진 월을 더 이전 월로 채우지 않는다. 최소 기준선 월수와 최소 기사 수를 바꿔 결과를 비교했으며, 일부 월의 급증 판정은 설정에 따라 달라졌다(3.1).
- **태깅 재현율:** 정규식 HBM 태깅의 추정 재현율은 0.85다. 태깅이 놓친 기사는 HBM 보도 비중의 분자에서 빠지고 감성 분석 대상에서도 제외된다(2장).
- **뉴스 지표의 해석:** 보도 비중과 기업 언급 비율은 수집 기사에서 기술과 기업이 얼마나 자주 다뤄졌는지 보여준다. 감성은 기사에서 나타난 기업별 유리·불리한 평가를 분류한 결과다. 시장점유율과 매출은 별도의 사업 자료로 확인해야 한다.

## 7.5 협업과 개발 과정 (공동, 김한승 초안)

- **브랜치·PR:** `main`에 직접 커밋하지 않고 브랜치와 PR로만 합쳤다. 리포트를 장별 파일로 나눠 동시에 써도 충돌이 적었다. 그래도 같은 파일(리포트 6장, README, `conclusion.py`)을 함께 고치면서 충돌을 여러 번 해결했다.
- **환경 차이:** pandas 2.3.3에서 공시 근거를 다시 생성하자 기존 확인 표시 7건이 해제됐다. 팀 버전인 3.1.1로 맞춘 뒤 문제가 해결됐다. 의존성 명세에는 `pandas==3.1.1`과 응답 압축 해제에 필요한 `brotlicffi>=1.2`를 명시했다(#45, #51).
- **squash 머지로 사라진 변경:** 아래 PR이 머지된 뒤 위에 쌓은 브랜치를 그대로 올리자 변경이 빠지거나 두 번 들어갔다. #7은 main이 아닌 다른 브랜치로 머지됐고(#9로 다시 올림), #20 머지 때 README 행과 테스트 4개가, #25 머지 때 README 실행 순서 설명이 사라졌다(#23·#26에서 복원). 그 뒤로는 PR base를 항상 main으로 두고, 이미 머지된 브랜치에는 push하지 않으며, 머지 전 diff에서 README와 테스트 수가 줄지 않았는지 확인했다.
- **DB는 주고받지 않고 각자 다시 만들기:** SQLite 파일을 주고받으면 서로 덮어써 최신본을 알 수 없다. 대신 코드와 입력(DART 원본 zip, LLM 결과 CSV, 사람 라벨 CSV)을 공유하고 각자 DB를 다시 만든 뒤, `db --check`의 테이블별 행 수·기본키 지문·FK 위반으로 두 컴퓨터의 결과가 같은지 맞췄다(Day 2부터). 지문은 기본키만 보므로 `verified` 같은 값의 차이는 실행 출력의 건수로 따로 확인했다.
- **라벨 파일과 Excel:** 근거 확인 라벨을 Excel로 저장하자 접수번호(`rcept_no`)가 `2.0241E+13`처럼 지수 표기로 바뀌고 파일이 cp949로 저장되어 키가 깨졌다(두 번). 맨 끝에 문자열 `key` 열을 두어 키를 복구하고, 키가 깨졌는데 `key`가 없으면 실행을 멈추게 했다.
- **역할 경계:** 결론을 이슈 분석 화면과 요약 페이지 두 곳에서 만들 뻔했다. 결론은 요약 페이지(한도윤 화면, 김한승 숫자 계산·QA)로 모으고, 이슈 분석은 분석 결과만 보여 주도록 정리했다. 쓰지 않는 코드는 공동 PR로 정리했다 (#62).
- **AI 도구 사용:** 코드 작성과 점검에 Claude를 썼다. 실행 결과는 로그 파일로 공유하고, 사람이 원문(기사·공시 PDF)과 숫자를 직접 확인한 뒤 반영했다. API 키는 저장소·로그에 남기지 않았다.

## 7.6 다음에 다르게 할 것

1. 프롬프트 개선용 표본과 독립 평가용 표본을 처음부터 나눈다. 이번 프로젝트의 후속 평가에서는 프롬프트와 판정 기준을 확정한 뒤, 아직 라벨링하지 않은 51~100행을 활용한다.
2. 공시 인용은 원본 문서, 쪽 번호, 기간, 지표 정의와 함께 저장한다. 보고서와 대시보드에 표시할 인용문을 쪽별 추출 텍스트와 대조한다.
3. HBM 기술 경쟁, 실적, 고객사 공급, 투자 등 분석 질문에 필요한 주제를 반영해 뉴스 수집 키워드를 설계하고, 주제별 누락 가능성을 점검한다.
4. 프로젝트 시작 때 Python과 주요 패키지 버전을 고정하고 공통 실행·테스트 절차를 문서화한다.
5. 기업별 감성 판정 기준과 경계 사례를 검수 전에 합의한다. 판정이 갈릴 때는 기사 원문을 대조해 기준을 보완한다.
6. 평가 질문과 정답 근거 기준(같은 사실이 담긴 다른 공시도 정답으로 볼지)을 시험 전에 정한다. 이번에는 결과를 본 뒤 정답을 두 번 보정했다(7.4). 재정렬 시험 때처럼 새 기법을 시험하기 전에 확인용 질문 세트를 먼저 만들어 둔다.
7. LLM 결과는 같은 입력에서도 흔들리므로, 평가는 여러 번 실행해 점수를 범위로 보고한다.
