## disclosure_review_v1.csv — 공시 관련성 검수 (한도윤)

`python -m src.dart.relevance_review sample`이 만든 표본 134건. 수집한 공시가 프로젝트 질문에 실제로 관련 있는지 확인한다.

| 층 (`stratum`) | 표본 | 보는 것 |
|---|---:|---|
| A·D·J RAG대상 | 전수 (24·11·29) | 정밀도 |
| B·I RAG대상 | 무작위 20씩 | 정밀도 |
| I·J 제외 | 무작위 15씩 | 놓친 비율 (필터가 관련 공시를 잘못 뺐는지) |

**채우는 법:** `head`(본문 앞 300자)와 `context`(판정 단서 주변 발췌)를 보고 `label`을 채운다. 애매하면 `url`로 원문을 연다.

| label | 의미 | 예 |
|---|---|---|
| 2 | 직접: HBM 또는 HBM 관련 투자·제품·실적·고객을 다룸 | 사업보고서의 HBM 매출·R&D, HBM 라인 신규시설투자, 패키징 공장 보도 해명 |
| 1 | 간접: 메모리 사업·설비투자·실적·경영계획 등 HBM 판단의 배경 근거 | FAB 건설 매입, 영업(잠정)실적, 장래사업·경영계획 |
| 0 | 무관 | 자사주 보상 처분, 배당, 계열사 보험·급식 거래, 위임장 플랫폼 안내 |

- `note`: 애매한 이유, `labeler`: 판정한 사람 (예: `한도윤`, `claude_1차` → 사람 확인 후 이름으로 바꿈)
- 다 채우면 `python -m src.dart.relevance_review score` → `outputs/reports/disclosure_relevance_v1.csv`
- 표본을 다시 뽑으려면 `sample --force` (채운 라벨이 지워지므로 주의)

## issue_evidence_review_v1.csv — 급증 구간 근거 후보 확인 (공동)

`python -m src.dart.issue_evidence`가 급증 구간(`issues`)마다 근거 공시 후보를 만들어 이 파일에 빈 `verified`로 추가한다. 사람이 채운 값은 다시 실행해도 지워지지 않고 DB `issue_evidence.verified`에 반영된다. 이 파일을 git으로 공유하기 때문에, 각자 DB를 다시 만들어도 확인 결과가 같다.

| 열 | 내용 |
|---|---|
| `issue_id`, `rcept_no`, `news_id`, `match_type` | 후보 키 (고치지 않는다). `키워드` = 기사↔공시 연결, `기간` = 구간 안 사건성 공시(기사 없음) |
| `corp_name` ~ `url` | 판정용 참고 (공시명·제출일·대표 기사 제목·공시 링크). 읽을 때는 쓰지 않는다 |
| `verified` | `1` 이 공시(와 기사)가 급증의 배경 근거가 맞다 / `0` 기각 / 빈칸 미확인 |
| `note`, `reviewer` | 근거 요약 또는 기각 이유, 판정한 사람 |

- **판정 기준:** 공시 내용이 그 구간의 HBM 보도와 같은 사건을 다루면 `1`이다. 예: 신규시설투자 공시와 그 공장 보도, 잠정실적 공시와 HBM 실적 콘퍼런스콜 보도. 같은 회사가 같은 무렵에 냈을 뿐인 공시는 `0`이다. 예: 계열사 FAB 공사 거래, ADR 상장 풍문 해명.
- **HBM 공시인데 그 구간 보도에 없을 때:** `1`, note를 `공시 단독 | …`으로 시작한다. 기사가 없어도 회사가 HBM을 직접 공시했으면 근거로 둔다 (2026-11-17 결정, 예: 2024-12-20 SK하이닉스 인디애나 HBM 패키징 공장, SK하이닉스 실적 첨부). note에서 `공시 단독`만 골라 '보도되지 않은 HBM 공시' 목록을 만든다.
- **같은 날 원본과 [기재정정]이 함께 있을 때:** HBM 자료(첨부 포함)가 있는 쪽 = `1`, 다른 쪽 = `0`(note: ○○ 사용). 두 회사의 실적 공시는 원본에 경영설명회 자료(PDF)가 첨부되어 있어 원본 = `1`, [기재정정] = `0`이다. [기재정정]에는 첨부가 없거나, 월초 잠정실적 설명자료(1~2쪽)만 있다 (2026-11-17 결정, 4쌍 확인).
- **HBM 여부는 그 공시(본문+자기 첨부)로만 본다:** 다른 공시의 첨부에서 HBM용이라고 언급해도 인정하지 않는다 (예: 2024 SK하이닉스 M15X·용인 신규시설투자 = 0, 2026-11-17 결정).
- **첨부도 본다:** 공시 본문에 HBM이 없어도 첨부(경영설명회·Earnings Presentation PDF)에 HBM 내용이 있으면 HBM 공시로 본다. 수집 단계에서 첨부는 받지 않았으므로(본 문서만), DART 화면의 '첨부' 목록에서 확인하고 note에 '첨부 … PDF에 HBM'으로 적는다.
- **수동 근거:** 사람이 찾은 근거는 `match_type=수동` 행으로 직접 추가한다 (`rcept_no`나 `news_id` 중 하나 이상).
- 대시보드 근거 카드에는 `verified=1`만 올린다.
- **Excel로 열 때 주의:** Excel이 `rcept_no`를 `2.0241E+13`처럼 바꾸고 cp949로 저장한다. 맨 끝 `key` 열은 지우지 않는다. 다시 실행하면 `key`로 원래 키를 복구한다. `key`가 없는데 키가 깨져 있으면 실행이 멈춘다.
- **`note`의 `claude_1차 제안`:** Claude가 공시 원문과 기사를 대조한 1차 의견이다. `verified`는 사람이 채운다. `verified`가 비어 있어도 note가 있는 행은 다시 실행할 때 남는다.


## issue_summary_v1.csv - 급증 구간 사건 요약 (공동)

`issues.summary`(사건 요약)의 원본입니다. `spike_detection`이 실행할 때마다 `summary`를 비우기 때문에, 요약은 DB가 아니라 이 파일에 둡니다. DB 반영은 `spike_detection`을 고치지 않고 따로 `python -m src.dart.issue_summary --apply`로 합니다 (확정 행만, 2026-11-18).

| 열 | 내용 |
|---|---|
| `issue_id`, `period` | 급증 구간 (`issues`와 같은 ID) |
| `summary` | 1~3문장. **보도:** 무엇이 보도됐나 / **공시 확인:** 근거 공시(`issue_evidence` `verified=1`)로 확인된 것 / 관련 공시가 없으면 없다고 쓴다 |
| `evidence_rcept_no` | 요약에 쓴 근거 공시 접수번호 (`; ` 구분) |
| `status` | `미작성` / `초안` / `확정` |
| `reviewer` | 쓴 사람·확정한 사람 (`claude_1차` → 확인 후 이름으로 바꾼다) |

- **쓰는 원칙:** 인과를 쓰지 않는다("공시 때문에 보도 증가" 대신 "같은 시기 공시로 확인"). 발언의 출처가 콘퍼런스콜(기사)이면 그렇게 적는다.
- `status=확정`인 행만 대시보드와 리포트 3.1에 쓴다.
- **점검:** `python -m src.dart.issue_summary`가 구간 누락·중복, status 값, `evidence_rcept_no`가 그 구간의 `verified=1` 근거인지 확인한다. 근거 중 요약에 안 쓴 공시는 경고로 보여 준다.
- **확정 방법:** 사람이 요약과 원문(공시 첨부·기사)을 대조한 뒤 `status`를 `확정`, `reviewer`를 이름으로 바꾸고 `--apply`를 실행한다. 2026-11-18 원문 대조(첨부 자료 인용·기사 건수)는 `note`에 적었다. 6구간 모두 아직 `초안`이다.

## qa_eval_v1.csv — 공시 Q&A 평가 질문 (한도윤)

`python -m src.rag.evaluate`의 입력이다. 사람이 질문을 고르고, 청크 원문을 찾아 정답 근거와 핵심 사실을 정했다 (2026-11-18, 24문항: 답변 19 + 거절 5).

| 컬럼 | 의미 |
|---|---|
| `qid`, `category` | 질문 번호, 유형 (첨부·수치, 정기보고서, 풍문 해명, 위임장(D), 비교, 기업 없음, 거절·대상 밖 등) |
| `expected` | `답변` 또는 `거절` |
| `gold_groups` | 정답 근거 공시 `rcept_no`. `;`는 "이 중 하나", `\|`는 "그룹마다 하나씩 모두" (비교 질문은 두 회사 근거가 모두 있어야 함). 거절 질문은 빈 값 |
| `answer_pattern` | 답변에 들어 있어야 할 핵심 사실 (정규식). 예: `70` (SK '24.3Q HBM 매출 QoQ +70% 이상) |
| `note` | 근거 위치와 판단 메모 |

- **정답 근거 추가 규칙:** 평가 결과를 본 뒤 정답을 바꾸면 결과를 좋게 만드는 쪽으로 기울 수 있다. 그래서 '같은 사실을 담은 다른 공시'를 원문으로 확인했을 때만 추가하고, `note`에 그 사실을 적는다. 예: Q12에 장래사업ㆍ경영계획 정정 공시(2024년 시설투자 실적 53.6조원)를 추가했다. 답변이 불완전하면 정답 근거를 넓히지 않는다 (Q16).
